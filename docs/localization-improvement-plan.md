# 문화관 비전 보정 개선안

2026-11-12. 현재 구현과 저장된 같은 영상의 결과를 분석한 개선안이다. 이번 분석에서는 운영 코드의 승인 조건이나 설치 앱을 변경하지 않았다.

## 결론

우선순위는 **문 인스턴스의 연속 추적 → 깊이 없이도 사용하는 경로 제한 2D 관측 매칭 → 여러 벽 선분의 방향 추정 → 실제 AR 데이터 검증**이다. 현재의 metric 점 매칭과 삼각측량은 충분한 기하가 있을 때 사용하는 보조 경로로 유지한다.

가상의 등속 위치·시선을 실제 영상 자세처럼 사용한 현재 시험은 현장 정합 성능을 평가하는 데 한계가 있다. 영상의 실제 인식 실패, 구현의 관측 손실, 잘못 가정한 카메라 기하를 구분해야 한다.

## 1. 확인한 실패 지점

원본 영상 SHA256 `d8d98cb2f8e5da06a8e88ff94640c3289e9e67d1e4dedd4279718ec435cde7b5`, 동일한 237개 시각을 분석했다. 재현 스크립트는 `model-tests/ade20k/diagnose_localization.py`, 수치는 `results/temporal-wall-replay-20261112/failure-diagnosis.json`에 있다.

| 단계 | 통과 프레임 |
|---|---:|
| 일정 면적 이상의 door 클래스 픽셀이 존재 | 89 |
| 문 연결 요소·면적·평균 신뢰도 0.6 통과 | 28 |
| 문 후보 신뢰도 0.65 통과 | 13 |
| 문 후보 시간 안정성도 통과 | 3 |

| 안정적인 계단 후보가 복도 구간에 있음 | 2 |

89→28은 신뢰도만의 손실이 아니다. 관심 클래스 면적 집계와 객체별 연결 요소 검사 사이의 차이다. 시간 안정성의 경우 현재 프레임 bbox 중심이 직전 프레임에서 화면의 10% 이내로 움직여야 한다. 보행·회전·가림으로 대상이 화면에서 움직이면 같은 문도 연결이 끊길 수 있다. 삼각측량은 이 취약한 후보 연결에 추가적인 시차·교차 검사까지 요구한다.

누적 창이 12초여도 처음부터 안정적인 관측으로 들어오는 수가 적으므로, 창을 길게 늘리는 것만으로 해결하기 어렵다. 실제 문이 아닌 동일 노드 근처의 잡음이 오래 남을 수도 있다.

## 2. 조건만 완화하는 방안은 우선하지 않는다

벽 방향에서 누락 프레임을 허용하고 2초 안의 3개 관측을 4도 범위로 묶는 단순한 가정 실험을 했다. 99.5초 부근에 중앙값 약 9.02도의 방향 보정이 가능하지만, 이 시험에 주입한 회전 오차는 약 1.79도다. 가상 정답과 약 **7.23도** 어긋난다.

이것은 실제 벽의 방향이 잘못됐다는 측정이 아니다. 실제 카메라 회전과 intrinsics가 아닌 가정 값을 사용한 시험에서, 승인을 늘리는 것이 정확도 개선을 뜻하지 않는다는 반례다. 이 느슨한 조건을 앱에 적용하지 않았다.

## 3. 최우선: 검출과 추적의 역할을 분리한다

현재 모델은 0.5초마다 문을 다시 검출한다. 중간 프레임의 시각적 연속성이 거의 쓰이지 않는다.

제안:

1. 모델은 기존 약 2Hz로 재검출한다. 그 사이의 프레임에서는 문틀·문 표면의 특징점을 약 10~15Hz 목표로 추적한다. 이 주기는 구현 후 기기 성능으로 결정하며 현재 측정 성능이 아니다.
2. 특징점의 앞→뒤 광학 흐름 일치, RANSAC 기하, AR 카메라 운동 예측을 결합해 동일 문 ID를 유지한다. 화면 중심 거리만으로 ID를 정하지 않는다.
3. 문 박스·마스크 내부의 여러 특징점으로 확인한다. 열린 문짝이 움직이면 문틀/고정 개구부를 우선하고, bbox 중심의 이동을 문 위치 이동으로 받아들이지 않는다.
4. 낮은 신뢰도 후보는 즉시 metric 매칭에 넣지 않고 임시 트랙에 보관한다. 다음 프레임의 외형·운동·기하가 일치할 때 확인 상태로 올린다. 이는 승인 임계값을 일괄 낮추는 방식과 다르다.
5. 부분 가림과 짧은 검출 누락에는 불확실성을 키우면서 ID를 유지하되, 재관측에서 불일치하면 폐기한다.

OpenCV의 `calcOpticalFlowPyrLK`는 프레임 사이 특징점 이동을 계산하는 공식 API다. 이 API 사용이 현장 성능을 보장하는 것은 아니며, 앞뒤 검사와 객체 대응 검증을 직접 설계해야 한다.

근거: [OpenCV Object Tracking](https://docs.opencv.org/4.13.0/dc/d6b/group__video__track.html).

### 이미 있는 문 전용 모델 활용

작업 공간에는 같은 영상의 YOLO26n doorway 검출 결과가 이미 있다. 원본과 캐시 SHA256을 대조하고 같은 237개 시각을 비교했다.

- 기존 SegFormer 객체 후보: door 검출 28프레임.
- 기존 YOLO 캐시: door 또는 doorway 검출 52프레임, 복도 구간 34프레임.
- 두 경우 모두 한 프레임의 후보 수는 최대 2개였다. 문 전용 검출기를 사용해도 단일 프레임의 3개 구조물 요구는 해결하지 못한다.

이 수치는 정답률 순위가 아니다. 클래스 의미와 검출 점수/픽셀 확률의 기준이 다르고 오검출 정답도 없다. **먼저 기존 캐시로 올바른 문의 지속 추적 비율을 비교할 가치가 있다**는 근거다. 추가 학습·다운로드 전에도 비교할 수 있다.

실험적으로는 문/열린 출입구 인스턴스에 문 전용 검출기, 벽·바닥·계단에 SegFormer를 쓰는 역할 분담이 타당하다. 모바일 모델 변환·속도·메모리·패키지 크기와 해당 모델의 AGPL-3.0 조건은 실제 채택 전에 확인해야 한다. 현재 폰에 이 추가 모델을 설치한 상태는 아니다.

## 4. 경로 위의 2D 관측으로도 위치 후보를 좁힌다

사용자의 출발점·층·예정 경로는 이미 알려져 있다. 따라서 관측한 문을 모두 3D 점으로 만들어야만 비교하는 구조는 너무 제한적이다.

제안 상태:

- 현재 복도 링크와 링크 위 진행 거리 `s`.
- 복도 중심선에서의 좌우 편차 `d`.
- 경로 방향 대비 카메라 회전 오차 `yaw`.
- 가능한 문 ID와 후보별 확률/불확실성.

ARCore 상대 이동으로 다음 위치 후보를 예측하고, 영상의 문 좌우 방향·관측 순서·문 사이 상대 간격·계단 전환을 이용해 후보 확률을 갱신한다. 실제 카메라 intrinsics와 촬영 Pose로 지도상 문 위치가 어느 방향에 보여야 하는지 계산하면, 깊이를 직접 측정하지 않고도 방향 관측의 오차를 비교할 수 있다.

반복되는 문 배치에서는 하나로 즉시 결정하지 않는다. HMM/입자 필터 또는 작은 후보 집합의 누적 점수로 여러 가능성을 유지한다. 같은 문이 세 번 관측된 것을 서로 다른 기준점 세 개로 세지 않는다.

최종 변환은 관측으로 결정 가능한 성분만 갱신한다. 긴 직선 복도의 방향만 확인됐으면 yaw만, 좌우 편차만 근거가 있으면 횡방향만 보정한다. 진행 방향의 위치가 모호하면 해당 성분을 유지한다. 충분한 Depth/삼각측량이 들어오면 기존 2D rigid 매칭을 강한 제약으로 결합한다.

이것은 아직 구현하지 않은 후속 설계다. 단일 문 관측 하나로 위치와 회전을 모두 알아낼 수 있다고 가정하지 않는다.

## 5. 벽 방향은 한 선분 선택에서 다중 선분 추정으로 바꾼다

현재 추정기는 바닥 투영 후 예상 지도 축과 가장 가까운 선분 하나를 선택한다. 근거의 양보다 지도 예상값과의 근접성이 선택 기준이어서, 잡음으로 선택 선분이 바뀌기 쉽다. 선분 길이·픽셀 수에서 만든 신뢰도도 실제 각도 오차의 보정된 확률은 아니다.

제안:

1. 벽·바닥 경계와 실제 영상의 문틀·천장·복도 장선을 함께 수집한다. 사람이 가린 경계나 불연속을 구분한다.
2. 여러 선분에서 공통 방향/소실점을 robust fitting으로 추정하고, ARCore의 중력·roll/pitch와 실제 intrinsics로 yaw를 계산한다.
3. 서로 독립된 선분 수·분포·재투영 잔차에서 각도 불확실성을 산정한다. 하나의 짧은 선분보다 여러 곳의 일치가 강한 증거가 되게 한다.
4. 누락 한 프레임에 이력을 모두 초기화하지 않고 짧은 시간 창의 가중 중앙값/원형 분포로 합의한다. 단, 중간 회전·코너·추적 손실에서는 창을 재설정한다.
5. 복도 끝의 정면 벽과 옆 벽을 구분하고, 양쪽 방향이 모호한 코너에서는 방향 보정을 유지하지 않는다.

공간 선분이 영상에 투영되는 관계는 카메라 행렬과 실제 회전에 의존한다. 현재 시험의 임의 intrinsics/시선에서는 벽 알고리즘만 개선해도 성능 평가가 왜곡될 수 있다.

근거: [OpenCV camera model 및 calibration](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html).

## 6. 영상 시험과 실제 앱 검증을 분리한다

### 기존 일반 MP4로 바로 할 수 있는 것

- 동일 문 추적 지속 시간·ID 유지·재검출 후 재연결을 비교한다.
- 문/계단의 지도 ID를 확인할 수 있는 장면과 통과 시각 6~10곳을 평가용으로 지정한다.
- 추정한 관측 순서와 지정한 ID/시각이 일치하는지 본다. 평가용 일부 시각은 보정 입력에서 제외해 검증에만 사용한다.
- 광학 흐름/특징점 기하로 상대 카메라 운동을 추정해 등속 가정과 비교한다. 단안 영상의 `recoverPose`는 절대 이동 크기를 주지 않으므로 미터 단위 정확도를 곧바로 주장하지 않는다. 그래프 거리로 scale을 정하면 그 그래프 제약에 의존한 시험임을 명시한다.

근거: [OpenCV recoverPose — translation is only known up to scale](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html).

### 현장에서 확보할 데이터

기존 앱의 녹화 기능을 사용해 같은 경로의 영상·센서 데이터를 기록한다. custom track 또는 별도 동기화 로그에 촬영 시점 intrinsics, 원점 상대 Pose, 바닥 높이, 이미지 좌표 변환, 추적 상태, 가용 Depth의 시각을 보존한다. ARCore 녹화가 사용자 정의 데이터를 자동 저장하는 것은 아니므로 필요한 항목을 명시적으로 기록해야 한다.

근거: [ARCore Recording and Playback](https://developers.google.com/ar/develop/recording-and-playback), [Custom data tracks](https://developers.google.com/ar/develop/java/recording-and-playback/custom-data-track).

## 7. 권장 구현·평가 순서

| 순서 | 구현/시험 | 통과 여부를 판단할 지표 |
|---|---|---|
| 1 | 기존 검출 결과 + 특징점 추적, 임시/확인 트랙 분리 | 올바른 동일 문 ID 지속 시간, ID 교체·잘못된 재연결 수 |
| 2 | 같은 경로의 문 순서/좌우 방향을 사용하는 2D 후보 매칭 | 평가용으로 남긴 문 ID·통과 시각의 정답 일치, 모호한 구간의 보류 |
| 3 | 다중 선분/소실점 + 중력으로 복도 방향 추정 | 독립적으로 확인한 직선 구간의 방향 일관성, 코너에서의 오보정 |
| 4 | 실제 AR 녹화 재생으로 1~3을 결합 | 보정 전후 거리·yaw 오차, 오보정 횟수, 전체 처리 지연 |

승인 횟수만 늘어나는 것을 개선 지표로 삼지 않는다. 새로운 기능마다 기존 결과와 동일한 입력·동일한 평가 지점을 비교하며, 픽셀/ID 평가와 metric 위치 평가는 구분한다.

이번 산출물은 실패 원인 진단과 후속 설계다. 광학 흐름 추적·경로 위 확률 매칭·새 소실점 추정기를 구현하거나 폰에 배포한 것으로 기록하지 않는다.
