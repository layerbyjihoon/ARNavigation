## 통합본 실내 전환 후 자동 시작 (2026-11-25)

실외에서 실내로 전환할 때 전달한 첫 호실 경로는 안내 시작 버튼을 누르지 않아도 시작을 대기한다.
첫 바닥 인식 위치를 별도 앵커로 고정하는 방식은 사용하지 않는다. 카메라 추적·방향 정렬·바닥이
준비되면 임시 AR 좌표 기준으로 안내를 시작하고, 문·계단 및 복도 구조를 도면과 비교하는
기존 자동 위치·방향 보정으로 경로를 갱신한다. 모델 실행 및 보정 스위치는 처음부터 켠다.
보정은 신뢰 조건을 통과한 결과만 적용하고, 최대 이동 1.5m·회전 10° 제한을 유지한다.
이 기능은 근거리 정렬 보정이며 건물 전체에서 임의의 시작 위치를 찾는 절대 측위가 아니다.
문화관 지도 경로의 출발 노드는 F1_C006·F1_C007 중점으로 유지한다.
자동 요청은 전환 시 한 번만 적용하며, 초기화·경로 재선택·안내 완료 후에는 재시작하지 않는다.

문화관 실내 경로는 F1_C006과 F1_C007 사이 중점인 X 12.251m, Z 3.0465m를
시작점으로 고정한다. 이전 도면 오른쪽(+X) 1m 오프셋은 제거한다. 시작 노드
F1_START_C006_C007을 두 복도 노드에 각각 2.0845m 간선으로 직접 연결한다.
출발점 선택을 비활성화하고 실제 경로 계산과 반환 데이터에도 이 시작점을 사용한다.
사용자는 실내 안내 시작 시 이 위치에 서 있어야 한다. 실외 정문 GPS 좌표와 별개의 기준이다.
실외→실내 전환은 기존처럼 CameraX를 완전히 종료한 뒤 새 ARCore 세션을 여는 방식으로 유지한다.

## 통합본 문화관 앞문 목적지 고정 (2026-11-25)

사용자가 폰 지도에서 선택하고 앞문으로 확인한 좌표(위도 37.49637, 경도 126.95442)를
문화관의 실외 목적지로 사용한다. 문화관은 Places의 건물 대표 좌표로 대체하지 않는다.
검색 후 호실을 설정하는 경로와 기존 호실을 다시 설정하는 경로 모두 같은 앞문 좌표로
실외 경로 요청 및 실내 진입 근접 판정을 수행한다. 실내 안내는 기존 진입 확인 조건을 유지한다.

## 통합본 문화관 호실 사전 설정 (2026-11-25)

홈 검색 또는 AR 경로 변경에서 문화관을 선택하면 추가 확인 없이 호실 선택을 연다.
호실 선택을 취소하면 기존 목적지·호실을 유지한다. 호실을 설정하면 실내 경로를 사전 저장하고
문화관까지의 실외 경로를 준비한 뒤 지도에 AR 안내 시작 버튼을 표시한다. AR은 사용자가
시작 버튼을 눌러야 시작하며, 호실 설정만으로 실내 안내를 실행하지 않는다. 실제 실내 전환은
기존 GPS 근접·Vision 진입 확인 및 카메라 인계 완료 조건을 만족한 뒤에만 활성화한다.

지도에서 직접 목적지를 선택하는 기능과 문화관 호실 선택은 유지한다.

## 통합본 실외 AR 방향 화살표와 API 안내 (2026-11-26)

실외 AR은 목적지까지의 경로 띠·반복 삼각형·가상 바닥 투영을 사용하지 않고, 화면의 카드 사이에
단일 하늘색 방향 화살표를 표시한다. 현재 GPS 위치에서 선택한 목적지까지의 직선거리가 50m 이내면,
경로 투영이나 10m 앞 지점을 사용하지 않고 현재 GPS 위치에서 목적지 좌표를 직접 바라본다.
문화관은 지정된 출입구 좌표를 사용한다. 50m를 초과하면 현재 위치를 진행 중인 경로 구간에 투영한 뒤
경로를 따라 10m 앞 지점의 카메라 상대 방향을 나타낸다. 뒤쪽은 아래로 회전한다.
10m 안에 다음 안내 지점이 있으면 그 지점까지만 바라본다. 아래 경로 투영 규칙은 50m 초과 구간에 적용한다.
실내 진입 판정 시작 거리 30m와 비전 전환 조건은 유지한다.
경로 허용 범위(35m) 안에서는 투영한 위치에서 앞 지점으로의 진행 방향을 사용해 GPS 좌우 오차가
화살표를 경로선 쪽으로 꺾지 않도록 한다. 범위 밖에서는 실제 GPS에서 경로 복귀 지점을 바라본다.
투영 위치와 안내 지점이 겹치면 해당 구간의 진입 방향을 유지한다.
아직 지나지 않은 안내 지점을 넘어 가까운 후반 루프로 투영하지 않는다. 실내 ARCore 경로 표시는 유지한다.
상단 안내는 TMAP 안내 지점의 회전 종류·설명을 사용한다. 일반 형상 점과 출발·직진 지점을
넘어 다음 회전·횡단보도·계단 등의 안내를 찾고, 현재 활성 지점까지의 거리와 그 이후 경로
정점 사이 거리를 합쳐 '200m 앞에서 좌회전하세요'처럼 갱신한다. API가 제공하지 않은 회전을
임의로 만들지 않는다. GPS가 불확실하면 거리 없이 안내를 유지한다. 방향 센서가 불확실하면
화살표를 숨기되 API 안내는 계속 표시하며 8자 보정 문구와 각도 안내는 표시하지 않는다.

## 통합본 실외 웨이포인트 통과 판정 (2026-11-25)

실외 중간 웨이포인트는 반경 도달·위치 갱신 사이 통과뿐 아니라 경로선에 투영한 진행 거리로도
통과를 판정한다. 경로 이탈 허용 범위 안에서 다음 구간으로 진행한 것이 GPS 오차보다 분명하면
지나친 지점을 넘긴다. 가까운 평행 구간이나 교차 구간이 모호할 때는 현재 구간을 우선하고,
나중 구간을 거꾸로 움직이는 것으로 투영되면 건너뛰지 않는다. 목적지 도착 판정은 유지한다.

## 통합본 2D 남은 경로 표시 (2026-11-25)

목적지 후보를 선택해 목적지로 설정 창을 표시할 때는 해당 건물이 보이도록 목적지 중심으로 이동한다.
목적지로 설정 버튼을 누르면 현재 위치 중심으로 이동하고, 최초 경로 응답의 전체 경로 맞춤이 이를 덮어쓰지 않는다.
안내 중 2D 지도를 열면 현재 위치를 중심으로 한 번 이동한다. 위치나 지도 준비가 늦으면 준비된 뒤 한 번 이동하며, 이후 일반 위치 갱신에서는 사용자의 지도 조작을 유지한다.

2D 지도에는 웨이포인트 마커를 표시하지 않는다. 웨이포인트는 AR 방향 화살표와 API 회전 안내 거리 및 남은 경로 계산에 계속 사용한다.

2D 지도는 유효한 GPS가 갱신될 때 현재 위치부터 목적지까지의 남은 경로만 표시한다.
현재 위치를 경로의 남은 구간에 투영해 지나온 선을 제거하고, 현재 위치가 선에서 떨어져 있으면
현재 위치와 투영점을 연결한다. 새 경로를 받은 경우에만 전체 남은 구간에 맞춰 카메라를 조정하며
일반 GPS 갱신에서는 사용자의 지도 확대·이동을 유지한다. 위치가 불확실하면 마지막 표시를 유지하고
도착 시 경로 선을 지운다. 이 표시 갱신만으로 경로 API를 다시 호출하지 않는다.

## 통합본 실외 카메라 방향 기준 보정 (2026-11-25)

실외 방위는 화면 회전 방향이 아니라 후면 카메라 광축(-기기 Z)의 수평 방위를 사용한다.
기기 센서 좌표에 화면 회전 보정을 중복 적용하지 않으며, 가로 화면에서도 동일한 카메라 방위를 유지한다.
카메라가 거의 수직 위/아래를 보는 경우 수평 방위를 확정할 수 없어 안내 화살표를 숨긴다.
GPS·자기장 간섭에 의한 현장 오차는 별도 검증 대상으로 유지한다. 실외 표시에는 가상 바닥 원근 투영을 사용하지 않는다.

## 1. 제품 개요

AR Navigation은 숭실대학교 캠퍼스에서 사용자가 현재 위치로부터 특정 건물의 강의실까지 이동할 수 있도록 카메라 화면 위에 AR 방향 화살표를 표시하는 Android 애플리케이션이다.

P0와 P2 실외 안내는 모두 앱이 GPS 위치와 기기 방향을 처리하고 카메라 화면에 AR 방향 화살표를 표시한다. P0는 Google Maps Platform이 반환한 보행 경로와 다음 웨이포인트를 사용하고, P2는 자체 실외 경로 탐색 모델이 계산한 경로와 다음 웨이포인트를 사용한다. 실내에서는 자체 Vision Model이 사전에 등록된 Natural Landmark를 인식해 절대 위치를 결정하고, 그 위치를 기준으로 ARCore의 VIO(Visual-Inertial Odometry)가 사용자의 상대 이동을 추적한다. 경로는 층 정보를 포함한 2.5D 그래프에서 A* 알고리즘으로 계산한다.

## 2. 문제 정의

캠퍼스 방문자와 학생은 다음 문제를 겪는다.

- 건물명은 알아도 캠퍼스 내 정확한 위치와 적절한 출입구를 찾기 어렵다.
- 건물에 진입한 뒤에는 GPS 정확도가 낮아지고 일반 지도만으로 현재 층과 방향을 판단하기 어렵다.
- 강의실 번호 체계, 복도 구조, 계단 및 엘리베이터 위치가 건물마다 달라 목적지 도착까지 시행착오가 발생한다.

## 3. 목표 및 성공 기준

### 3.1 제품 목표

1. 사용자가 Google Maps 기반 검색·보행 경로와 카메라 AR 화살표로 목적 건물 또는 권장 출입구까지 안내받을 수 있다.
2. 건물 진입 후 Natural Landmark를 통해 실내 절대 위치와 층을 결정할 수 있다.
3. ARCore VIO로 실내 이동을 연속 추적하고 AR 화살표로 다음 진행 방향을 표시할 수 있다.
4. 층간 이동을 포함한 2.5D 최단 경로를 계산하고 경로 이탈 시 재탐색할 수 있다.
5. 위치 신뢰도가 낮을 때 잘못된 방향을 단정적으로 표시하지 않고 복구 행동을 안내할 수 있다.
6. P2에서 Google 경로 탐색에 의존하지 않고 자체 실외 경로 탐색 모델의 결과로 같은 AR 안내 경험을 제공할 수 있다.

### 3.2 단계별 성공 지표

측정값은 파일럿 대상 건물과 테스트 경로를 먼저 확정한 뒤 베이스라인 테스트로 보정한다. P0에서는 Google Maps 기반 건물 도착, P1에서는 건물 내부의 강의실 도착, P2에서는 자체 실외 AR 안내에 의한 건물 도착을 하나의 성공 세션으로 본다.

| 단계 | 지표 | 목표 |
|---|---|---:|
| P0 | 목적 건물 도착 성공률 | 테스트 경로의 95% 이상 |
| P0 | 건물 검색 및 Google 보행 경로 생성 성공률 | 유효한 테스트 목적지의 95% 이상 |
| P0 | GPS 갱신 후 AR 안내 정보 반영 시간 | 2초 이하 |
| P0 | 유효한 위치·방향 상태에서 Google 경로의 올바른 다음 웨이포인트 표시율 | 테스트 관측의 90% 이상 |
| P0 | 치명적 오류 없는 세션 비율 | 99% 이상 |
| P1 | 목적 강의실 도착 성공률 | 테스트 경로의 90% 이상 |
| P1 | Natural Landmark 인식 성공률 | 등록 지점, 지정 촬영 조건에서 90% 이상 |
| P1 | 랜드마크 인식 후 절대 위치 초기화 시간 | 중앙값 3초 이하 |
| P1 | 경로 이탈 감지 후 재탐색 시간 | 2초 이하 |
| P1 | AR 안내 프레임률 | 지원 단말에서 중앙값 30 FPS 이상 |
| P2 | 자체 경로 탐색 성공률 | 연결 가능한 테스트 경로의 95% 이상 |
| P2 | 자체 경로 이탈 감지 후 재탐색 시간 | 2초 이하 |
| P2 | 자체 경로 기반 실외 AR 안내의 목적 건물 도착 성공률 | 테스트 경로의 95% 이상 |

### 3.3 출시 Priority 정의

Priority는 요구사항의 중요도 표현이 아니라 **구현 및 출시 순서**를 의미한다. 선행 단계의 출시 기준을 충족한 뒤 다음 단계로 진행한다.

| Priority | 사용자에게 제공하는 결과 | 포함 범위 | 완료 조건 |
|---|---|---|---|
| **P0 — Google 경로 기반 실외 AR 내비게이션** | Google 보행 경로를 AR 화살표로 따라 목적 건물까지 도착 | Places 기반 건물 검색, Routes API 보행 경로·웨이포인트, GPS 위치·정확도, 기기 방향, CameraX 방향 오버레이, 경로 진행·도착 판정, 2D 지도 대체 화면 | 사용자가 Google 경로의 다음 웨이포인트를 가리키는 AR 화살표를 따라 목적 건물 또는 권장 출입구까지 도착할 수 있음 |
| **P1 — 실내 강의실 안내** | 건물 진입 후 선택한 강의실까지 도착 | 강의실 검색, 실내 2.5D 그래프, Vision Model, Natural Landmark 절대 측위, ARCore VIO, A*, 층간 이동, AR 화살표, 재측위 | 사용자가 지원 건물의 출입구에서 목적 강의실까지 안내받을 수 있음 |
| **P2 — 자체 경로 기반 실외 AR 내비게이션** | 자체 경로 탐색 결과를 AR 화살표로 따라 목적 건물까지 도착 | 자체 실외 지도·노드·간선, 자체 경로 탐색 모델, 경로 이탈·재탐색, P0와 동일한 GPS·방향·카메라 AR 안내 UI | Google Routes API 없이 자체 경로 탐색 결과의 다음 웨이포인트를 가리키는 AR 화살표로 목적 건물까지 도착할 수 있음 |

- P0 목적지는 **건물 또는 권장 출입구**이며 경로 탐색은 Google Maps Platform에 위임하지만, 경로 진행 상태와 다음 웨이포인트의 AR 화살표 표시는 앱이 담당한다.
- P1은 P0의 건물 도착 흐름을 재사용하고, 목적지가 강의실이면 권장 출입구에서 실내 안내를 이어간다.
- P2는 P0의 GPS·방향 센서·카메라 AR 안내 UI를 재사용하고 Google 경로 공급자만 자체 실외 경로 탐색 모델로 교체하는 후속 단계다.
- 표에서 `Future`로 표시한 기능은 P0/P1/P2 완료 조건에 포함하지 않는다.

### 3.4 비목표

- 모든 숭실대학교 건물과 강의실을 최초 버전부터 지원하지 않는다.
- 휠체어 접근성 경로는 검증된 접근성 데이터가 준비되기 전에는 일반 경로와 혼합 제공하지 않는다.
- 실시간 혼잡도, 친구 위치 공유, 음성 대화형 안내는 P0/P1/P2 범위에서 제외한다.
- ARCore 미지원 기기에서 완전한 AR 경험을 제공하지 않는다. 대신 2D 지도 안내를 대체 수단으로 제공한다.
- GPS만으로 실내 위치를 결정하지 않는다.

|---|---|

## 5. 전제 조건 및 제약

- P0/P1/P2는 사전 검증 및 데이터 구축이 완료된 1개 이상의 파일럿 건물을 대상으로 한다.
- P0는 Google Maps Platform의 가용성, API 키, 할당량, 과금 및 네트워크 연결에 영향을 받는다.
- 실내 각 층에는 2D 평면도, 노드, 간선, 층 연결 지점 및 Natural Landmark 메타데이터가 준비되어야 한다.
- Natural Landmark는 별도 마커를 부착하지 않고 표지판, 문, 벽면 특징 등 기존 환경 요소를 사용한다.
- 실내 위치 정확도는 조명, 사람에 의한 가림, 공간 구조 변경, 카메라 성능 및 ARCore 추적 상태에 영향을 받는다.
- 네트워크 단절 상황을 고려해 선택한 건물의 지도, 랜드마크 메타데이터, Vision Model은 로컬 캐시를 지원한다.
- AR 기능은 ARCore 지원 기기를 기준으로 하며 지원 여부를 런타임에 확인한다.

## 6. 핵심 사용자 여정

### 6.1 목적지 선택

1. 사용자가 앱을 실행한다.
2. P0 또는 P2 실외 AR 안내 시작 시 위치·카메라 권한의 사용 목적을 확인한다. P1 실내 안내에서도 허용된 카메라 권한 상태를 재사용한다.
3. P0에서는 Google Maps Platform을 통해 건물명이나 장소를 검색하고, P1에서는 건물명·강의실명·강의실 번호를 검색한다.
4. 검색 결과에서 목적지를 선택하고 경로 안내를 시작한다.

### 6.2 P0 Google 경로 기반 실외 AR 안내

1. 앱이 포그라운드 GPS 위치, 수평 정확도, 갱신 시각과 기기 방향을 수집한다.
2. Places 검색 결과와 사전 등록된 건물·출입구 데이터를 대조해 유효한 목적지를 확정한다.
3. Google Routes API가 반환한 보행 경로를 웨이포인트 목록으로 변환하고 2D 지도에 경로, 거리와 예상 시간을 표시한다.
4. 현재 위치와 경로 진행 상태로 다음 웨이포인트를 선택하고, 기기 방향에 대한 상대 방위각을 계산해 카메라 화면에 AR 화살표를 표시한다.
5. GPS 또는 방향 정확도가 낮으면 화살표를 숨기고 2D 지도와 복구 행동을 표시한다.
6. 경로 이탈 시 Google 경로를 다시 요청하고, API·네트워크 오류 시 원인과 재시도 또는 2D 제한 모드를 제공한다.
7. 도착 반경 안의 유효한 위치가 연속 확인되면 P0 안내를 완료하고, P1 목적지인 경우 실내 전환 절차를 안내한다.

### 6.3 P2 자체 경로 기반 실외 AR 안내

1. 앱이 포그라운드 GPS 위치, 수평 정확도, 갱신 시각과 기기 방향을 직접 수집한다.
2. 자체 실외 지도·노드·간선과 경로 탐색 모델로 현재 위치부터 목적 건물까지의 웨이포인트 경로를 계산한다.
3. 이후의 다음 웨이포인트 선택, 상대 방위각, 카메라 AR 화살표, 저신뢰 처리와 도착 판정은 P0와 같은 파이프라인을 사용한다.
4. 경로 이탈 시 자체 경로 탐색 모델로 현재 위치부터 재탐색한다.
5. P2는 Google Routes API가 없거나 실패해도 자체 경로 데이터가 있는 지원 구역에서 안내를 계속할 수 있어야 한다.

### 6.4 실내 초기 위치 결정

1. 앱이 사용자에게 주변 표지판이나 특징적인 공간을 천천히 비추도록 안내한다.
2. 자체 Vision Model이 카메라 프레임에서 Natural Landmark 후보를 인식한다.
3. 후보의 신뢰도, 현재 건물 후보, 관측 방향을 검증한다.
4. 임계값을 충족하면 랜드마크의 등록 좌표 `P=(x, y, floor)`와 관측 Pose를 이용해 실내 절대 위치 및 좌표계 변환을 초기화한다.
5. 임계값을 충족하지 못하거나 후보가 충돌하면 AR 안내를 시작하지 않고 재스캔 또는 2D 지도 선택을 제공한다.

### 6.5 실내 AR 안내

1. 현재 노드부터 목적 강의실 노드까지 A*로 경로를 계산한다.
2. ARCore VIO가 초기 절대 위치 이후의 상대 이동과 자세를 추적한다.
3. 앱이 다음 경로 세그먼트 방향으로 AR 화살표를 배치한다.
4. 계단 또는 엘리베이터 노드에 도착하면 층 전환 행동과 목표 층을 명확히 표시한다.
5. 새 층 도착 후 해당 층의 랜드마크 재인식을 유도해 누적 오차를 보정한다.
6. 목적지 도착 반경과 방향 조건을 충족하면 도착을 알리고 안내를 종료한다.

## 9. 시스템 아키텍처

### 9.1 전체 처리 흐름

```text
P0 실외
건물/출입구 검색 → Places API → Routes API → Google RouteProvider ─┐

P2 실외
자체 실외 지도/노드/간선 → 자체 경로 탐색 모델 → Custom RouteProvider ─┤
                                                                  ↓
GPS Location + Device Heading + 다음 웨이포인트 → 상대 방위/신뢰도 계산
                                                                  ↓
                                          Camera AR 방향 오버레이 + 2D 지도
                                                                  ↓
                                                   건물/출입구 도착

P1 실내
스마트폰 Camera
        ↓
자체 Vision Model
        ↓
Natural Landmark 인식 ──→ Landmark Repository
        ↓
실내 절대 위치 결정 P=(x, y, floor)
        ↓
ARCore VIO + 좌표계 변환/위치 융합
        ↓
2.5D Navigation Graph + A*
        ↓
AR Renderer
        ↓
AR 화살표 및 보조 안내 UI
```

P0와 P2는 `LocationProvider`, `HeadingProvider`, 웨이포인트 진행 판정과 카메라 AR 오버레이를 공유한다. 차이는 P0의 `GoogleRouteProvider`가 Google Routes API에서 경로를 가져오고, P2의 `CustomRouteProvider`가 자체 실외 경로 탐색 모델로 경로를 계산한다는 점이다. 두 방식 모두 출입구 도착 후 P1 실내 절대 위치 결정 단계로 전환할 수 있다.

## 10. 2.5D 지도 및 경로 모델

### 10.1 좌표 정의

- 실내 점은 `P=(x, y, floor)`로 표현한다.
- `x`, `y`는 건물별 로컬 평면 좌표이며 단위는 미터로 통일한다.
- `floor`는 문자열 표시명과 분리된 정렬 가능한 내부 층 ID를 사용한다. 예: 지하 1층은 `-1`, 1층은 `1`.
- 각 건물은 지도 원점, 축 방향, 실제 축척과 기준 방향을 가져야 한다.
- 실외 좌표(WGS84), 건물 로컬 좌표, ARCore 월드 좌표 사이의 변환 책임을 `localization` 모듈에 둔다.

### 10.2 핵심 엔터티

```text
Building
- id, name, mapVersion, origin, orientation

Destination
- id, buildingId, floor, roomName, nodeId

Node
- id, buildingId, x, y, floor, type
- type: HALLWAY | ROOM | ENTRANCE | STAIR | ELEVATOR | LANDMARK

Edge
- fromNodeId, toNodeId, distanceMeters, type, bidirectional
- type: WALK | STAIRS | ELEVATOR | DOOR
- accessibility, restricted, baseCost

Landmark
- id, buildingId, x, y, floor
- referenceHeading, modelClassId, confidenceThreshold, assetVersion
```

### 10.3 A* 정책

- 기본 비용 `g(n)`은 이동 거리와 간선별 가중 비용의 합이다.
- 휴리스틱 `h(n)`은 같은 층에서는 유클리드 거리, 다른 층에서는 평면 거리와 최소 층 전환 비용의 합을 사용한다.
- 최적 경로를 보장하려면 휴리스틱이 실제 최소 비용을 초과하지 않도록 구성한다.
- 계단 및 엘리베이터 간선만 `floor` 값을 변경할 수 있다.
- 폐쇄 구역과 운영 시간 제한은 간선을 비활성화하거나 비용에 반영한다.
- 사용자 위치가 간선 중간에 있을 경우 임시 시작 노드를 만들어 양 끝 노드와 연결한다.

### 10.4 실외 건물 안내 데이터

#### 10.4.1 P0/P2 공통 목적지 데이터

P0와 P2는 같은 건물·출입구 목적지를 사용한다. P0는 Google Maps Platform 경로를 사용하고 P2는 별도의 자체 실외 경로 데이터를 추가로 사용한다.

| 데이터 | 필수 필드 | 수집/생성 방법 | 품질 기준 |
|---|---|---|---|

| 건물 위치 | 대표 위도·경도, 도착 반경 | Google 장소 좌표와 출입구 현장 실측값 대조 | Google 지도 및 현장 위치와 대조 완료 |

#### 10.4.2 P0 Google 경로 데이터

- Routes API 응답에서 경로선, 보행 단계, 각 단계의 종료 좌표, 거리와 예상 시간을 `OutdoorRoute`와 `Waypoint`의 내부 공통 형식으로 변환한다.
- API 응답의 순서를 보존하고 좌표 누락, 빈 경로, 비보행 구간과 비정상적으로 먼 우회를 검증한다.
- Google 응답 원문에 결합된 라이선스·표시·캐시 제한을 준수하며 장기 저장이 허용되지 않는 데이터는 자체 데이터셋으로 전용하지 않는다.

| 데이터 | 필수 필드 | 수집/생성 방법 | 품질 기준 |
|---|---|---|---|
| 실외 노드 | `nodeId`, 위도·경도, 유형, 접근 가능 여부 | 보행로 교차점·회전점·출입구 현장 조사 | 실제 보행 가능 지점과 허용 오차 내 일치 |
| 실외 간선 | 양 끝 노드, 거리, 방향성, 경사·계단·제한 상태, 비용 | 캠퍼스 보행로와 현장 실측으로 생성 | 건물이나 통행 불가 구역을 관통하지 않음 |
| 경로 정책 | 보행 비용, 폐쇄 구간, 운영 시간, 접근성 속성 | 캠퍼스 운영 정책과 현장 조사 | 동일 입력에 재현 가능한 경로 반환 |
| 버전 정보 | 스키마·지도 버전, 작성일, 검수자, 무결성 값 | 배포 파이프라인에서 생성 | 앱과 호환되는 검증 버전만 활성화 |

- 자체 경로 탐색 모델은 P0의 `OutdoorRoute`와 `Waypoint` 공통 인터페이스를 구현해야 한다.
- 고립 노드, 중복 간선, 비정상 거리, 단절된 목적지와 금지 구역 횡단을 자동 검사한다.
- 모든 지원 목적지는 하나 이상의 시작 지점에서 도달 가능하고 현장 보행 테스트를 통과해야 한다.

### 10.5 P1 실내 노드 생성 데이터

노드는 평면도 위 임의의 점이 아니라 실제 보행 가능 경로와 의사결정 지점을 표현해야 한다. 원본 자료, 변환 산출물, 현장 검증 결과를 함께 버전 관리한다.

#### 10.5.1 원천 데이터

| 데이터 | 필수 내용 | 용도 |
|---|---|---|
| 층별 2D 평면도 | 벽, 복도, 문, 방, 계단, 엘리베이터, 출입구 | 보행 가능 영역과 노드 배치 기준 |
| 도면 메타데이터 | 건물 ID, 층 ID, 원점, 실제 축척, 북쪽/기준 방향, 좌표 단위, 도면 버전 | 픽셀/도면 좌표를 미터 단위 로컬 좌표로 변환 |
| 목적지 목록 | 강의실 ID, 공식명, 별칭, 건물, 층, 출입문 위치 | `ROOM` 노드 및 검색 인덱스 생성 |
| 연결 시설 목록 | 계단·엘리베이터·출입구 ID, 연결 층, 운행/개방 조건 | 층간 및 실외-실내 간선 생성 |
| 통행 정책 | 출입 제한, 일방통행, 운영 시간, 공사/폐쇄 상태 | 간선 활성화와 경로 비용 결정 |
| 현장 실측값 | 주요 점 사이 거리, 복도 폭, 문 위치, 층간 연결 확인 | 도면 오차 보정 및 그래프 검증 |

#### 10.5.2 생성 규칙과 산출 필드

- 복도 교차점, 방향 전환점, 출입구, 강의실 문, 계단, 엘리베이터, 랜드마크 위치에 노드를 생성한다.
- 긴 직선 복도는 AR 화살표 배치와 이탈 판정에 필요한 간격으로 중간 노드를 추가하되, 간격값은 현장 실험 후 구성값으로 관리한다.
- 벽이나 출입 불가능 영역을 가로지르는 간선을 생성하지 않는다.
- 각 노드는 `nodeId`, `buildingId`, `floor`, `xMeters`, `yMeters`, `type`, `sourceVersion`을 필수로 가진다.
- 목적지 노드는 `destinationId`, 층 전환 노드는 동일 시설을 묶는 `connectorId`, 랜드마크 노드는 `landmarkId`를 참조한다.
- 각 간선은 `edgeId`, 양 끝 노드, 실제 거리, 이동 유형, 방향성, 접근 가능 여부, 제한 상태, 비용을 가진다.
- 생성 결과는 기계 판독 가능한 JSON 또는 로컬 데이터베이스 형식으로 내보내며 스키마 버전을 포함한다.

#### 10.5.3 그래프 품질 기준

- 모든 지원 목적지는 하나 이상의 출입구에서 도달 가능해야 한다.
- 층 변경 간선은 동일 `connectorId`의 계단 또는 엘리베이터 노드 사이에만 존재해야 한다.
- 간선 거리는 좌표로 계산한 거리 및 현장 실측값과 허용 오차 내에서 일치해야 한다.
- 고립 노드, 중복 노드, 자기 자신으로 향하는 간선, 벽 횡단 간선을 자동 검사한다.
- 데이터 변경 시 `mapVersion`, 작성자, 작성일, 근거 도면 버전, 현장 검수 상태를 기록한다.
- 출시 후보 그래프는 최소 2인이 도면 검토와 실제 보행 테스트를 각각 완료해야 한다.

### 10.6 P1 Vision Model 학습 데이터

Vision Model 데이터는 랜드마크를 구분하는 이미지뿐 아니라 해당 인식 결과를 절대 위치로 변환할 수 있는 위치·방향 메타데이터를 포함해야 한다.

#### 10.6.1 랜드마크 선정 기준

- 장기간 위치와 외형이 유지되는 강의실 표지판, 층 안내판, 출입구, 고유한 벽면 구조를 우선한다.
- 서로 다른 층이나 복도에서 외형이 지나치게 유사한 대상, 이동 가능한 물체, 광고물, 쉽게 가려지는 대상은 제외한다.
- 복도 교차점, 출입구, 층 전환 직후 등 초기 측위 또는 오차 보정이 필요한 지점에서 관찰 가능해야 한다.
- 하나의 지점에서 단일 랜드마크가 가려져도 복구할 수 있도록 주요 구간에는 복수 후보를 확보한다.

#### 10.6.2 이미지와 라벨

| 분류 | 필수 데이터 |
|---|---|
| 원본 이미지/영상 프레임 | 원본 파일 ID, 촬영 시각, 기기 모델, 해상도, 카메라 방향, 촬영 세션 ID |
| 인식 라벨 | `landmarkId`, 클래스 ID, bounding box 또는 모델 방식에 필요한 영역 라벨, 가림·흐림 여부 |
| 절대 위치 라벨 | `buildingId`, `floor`, `xMeters`, `yMeters`, 랜드마크 기준 방향 |
| 관측 조건 | 랜드마크까지의 대략적 거리·각도, 조명 조건, 혼잡도, 세로/가로 방향 |
| 네거티브 샘플 | 미등록 복도, 일반 문·표지판, 유사 랜드마크, 사람 또는 물체에 가려진 장면 |
| 데이터 이력 | 라벨러, 검수자, 수집·라벨 버전, 사용 동의 또는 촬영 승인 상태 |

#### 10.6.3 수집 조건

- 각 랜드마크를 정면뿐 아니라 실제 보행 시 관찰 가능한 좌우 각도와 여러 거리에서 촬영한다.
- 오전·오후·야간 조명, 조명 켜짐/꺼짐, 그림자, 반사, 부분 가림, 사람 혼잡 등 운영 환경을 포함한다.
- 지원 예정 기기군의 서로 다른 카메라 화각과 화질을 포함한다.
- 연속 영상만으로 표본 수를 채우지 않고 촬영 날짜와 세션을 분산해 장면 다양성을 확보한다.
- 개인정보가 포함된 얼굴, 학생증, 화면 등은 수집 단계에서 제외하거나 비식별화하며 촬영 및 보관 정책을 준수한다.

초기 목표 수량은 랜드마크별 학습 이미지 200장 이상, 검증 50장 이상, 테스트 50장 이상으로 두되 단순 장수보다 조건 다양성과 독립 세션 수를 우선한다. PoC 결과에 따라 필요한 수량을 재산정한다.

#### 10.6.4 데이터 분할과 품질 기준

- 학습/검증/테스트 데이터는 동일 영상의 인접 프레임이 서로 다른 세트에 들어가지 않도록 **촬영 세션 또는 촬영 날짜 단위**로 분리한다.
- 최종 테스트 세트는 학습에 사용하지 않은 날짜, 동선 및 가능하면 다른 기기에서 수집한다.
- 클래스별 수량과 촬영 조건 분포를 점검하고 부족한 조건은 추가 수집한다.
- 라벨은 1차 작업자와 별도 검수자가 확인하며 랜드마크 ID, 층, 좌표 불일치는 출시 전에 100% 해소한다.
- 중복·심한 흔들림·노출 실패·잘못된 층 라벨을 자동 또는 수동 검사한다.
- 모델 평가는 전체 정확도만 보지 않고 랜드마크별 precision/recall, 오인식 행렬, 미등록 장면의 false positive rate, 기기·조명 조건별 결과를 기록한다.
- 모델 파일에는 `modelVersion`, 학습 데이터 버전, 클래스 목록 해시, 입력 규격, 평가 결과를 연결한다.

#### 10.6.5 데이터-런타임 연결 산출물

학습 완료 후 앱 배포 패키지에는 다음 산출물이 서로 같은 버전으로 제공되어야 한다.

1. 온디바이스 추론 모델과 입력 전처리 규격
2. `modelClassId`와 `landmarkId` 매핑 파일
3. 랜드마크별 `P=(x, y, floor)`, 기준 방향, 인식 임계값
4. 지원 건물·층과 모델/지도 호환 버전
5. 모델 및 메타데이터 무결성 값

하나라도 버전이 맞지 않으면 해당 실내 데이터 세트를 활성화하지 않는다.

## 11. 위치 결정 및 신뢰도 정책

### 11.1 실외

- P0와 P2 모두 위치 좌표, 수평 정확도, 갱신 시각, 기기 방향의 정확도와 현재 활성 웨이포인트를 함께 평가한다.
- 저속 또는 정지 상태에서는 GPS bearing만으로 방향을 확정하지 않고 회전 벡터 등 기기 자세 센서와 함께 사용한다.
- 화살표는 최종 목적지의 직선 방향이 아니라 선택한 경로의 **다음 유효 웨이포인트**를 가리켜야 한다.
- P0는 Google 경로 응답 상태, 네트워크, API 할당량과 경로 이탈 여부를 검증하고 필요하면 경로를 다시 요청한다.
- P2는 자체 경로 데이터 버전·무결성, 현재 위치 스냅 결과와 경로 이탈 여부를 검증하고 자체 모델로 재탐색한다.
- 위치·방향·웨이포인트 도달 임계값은 파일럿 실측으로 확정하며 원격 구성 또는 앱 설정값으로 조정 가능해야 한다.

### 11.2 실내

- 랜드마크 인식 신뢰도, 연속 프레임 일관성, 현재 건물 후보, 층 후보를 결합해 절대 위치 신뢰도를 산출한다.
- 랜드마크의 등록 Pose와 관측 Pose로 지도 좌표계에서 ARCore 월드 좌표계로의 강체 변환을 계산한다.
- VIO 이동량을 변환해 지도상의 현재 위치를 갱신한다.
- 시간이 지날수록 또는 이동 거리가 누적될수록 신뢰도를 감쇠시키고, 주요 랜드마크에서 재측위를 유도한다.
- 비현실적인 순간이동, 벽 통과, 불가능한 층 변경은 지도 제약으로 거부한다.
- 위치와 추적 상태를 `UNKNOWN`, `LOW`, `MEDIUM`, `HIGH`로 단순화해 UI와 경로 엔진에 제공한다.

## 12. 비기능 요구사항

### 12.1 성능 및 안정성

- Vision 추론은 UI 스레드에서 실행하지 않는다.
- 카메라 프레임 처리에는 backpressure를 적용하고 오래된 프레임을 폐기해 지연 누적을 방지한다.
- AR 렌더링 중 객체 생성과 메모리 할당을 최소화한다.
- 앱 백그라운드 전환, 화면 회전, ARCore 세션 일시정지 및 재개를 안전하게 처리한다.
- 모델 또는 지도 로딩 실패가 앱 전체 충돌로 이어지지 않아야 한다.

### 12.2 개인정보 및 보안

- 카메라 영상은 기본적으로 온디바이스 추론에만 사용하고 저장하거나 서버로 전송하지 않는다.
- 위치는 안내 중 포그라운드에서만 사용하며 P0/P1/P2에서는 백그라운드 위치 권한을 요청하지 않는다.
- 권한은 기능을 실제로 시작하는 시점에 요청하고 거부 시 제한 모드를 제공한다.
- 로그에 원본 이미지, 정확한 개인 이동 경로 또는 직접 식별자를 기록하지 않는다.
- 지도 및 모델 파일은 버전과 무결성을 검증한 뒤 활성화한다.

### 12.3 접근성 및 사용성

- 색상만으로 상태를 구분하지 않고 텍스트, 아이콘, 진동을 함께 사용한다.
- 카메라를 계속 보기 어려운 사용자를 위해 2D 지도와 텍스트 안내를 유지한다.
- 화면 요소는 Android 접근성 라벨과 충분한 터치 영역을 제공한다.
- 보행 중 화면 주시를 줄이도록 방향 변경과 층 전환 시점에 선택적 진동을 제공한다.

### 12.4 배터리 및 네트워크

- 안내 세션이 종료되거나 화면이 백그라운드로 이동하면 카메라, AR 세션, 위치 업데이트를 중지한다.
- P0/P2 실외 위치·방향 갱신 빈도와 P1 Vision 추론 빈도는 이동 및 화면 상태에 맞게 조절한다.
- 캐시된 지도와 모델이 있으면 네트워크 장애 중에도 핵심 실내 안내가 동작해야 한다.

본 프로젝트는 **Android Studio 기반으로 개발하며 Java 코딩 컨벤션을 필수로 준수한다.** 프로젝트에 formatter와 정적 분석 설정을 포함하고 CI에서 동일 규칙을 검사한다.

### 13.1 프로젝트 규칙

- Java 소스는 프로젝트가 채택한 Android/Java 스타일 설정으로 일관되게 포맷한다.
- 패키지명은 모두 소문자로 작성하고 기능 또는 계층 기준으로 구성한다.
- 클래스와 인터페이스는 `UpperCamelCase`, 메서드와 변수는 `lowerCamelCase`, 상수는 `UPPER_SNAKE_CASE`를 사용한다.
- 한 파일에는 하나의 public 최상위 클래스를 둔다.
- wildcard import를 사용하지 않고 사용하지 않는 import를 제거한다.
- 공개 API와 복잡한 좌표 변환, 신뢰도 계산, 경로 비용 정책에는 Javadoc을 작성한다.
- 매직 넘버 대신 의미 있는 상수 또는 구성값을 사용하고 단위를 이름에 포함한다. 예: `distanceMeters`, `timeoutMillis`.
- nullable 가능성을 명시하고 입력값과 외부 데이터는 경계에서 검증한다.
- 예외를 무시하지 않으며 사용자 복구가 가능한 오류와 개발 오류를 구분한다.

### 13.2 Android 구현 규칙

- Activity/Fragment는 화면과 수명주기 조정에 집중하고 Vision, 위치 융합, A* 로직을 포함하지 않는다.
- UI 상태는 단일 소스에서 관리하며 화면 회전과 프로세스 재생성 가능성을 고려한다.
- 긴 작업, 모델 추론, 파일 I/O는 백그라운드 실행기로 분리하고 메인 스레드에는 UI 갱신만 전달한다.
- Context, Camera, ARCore Session, Anchor, Image 등 수명주기 자원은 소유 주체를 명확히 하고 반드시 해제한다.
- 문자열, 색상, 크기는 리소스 파일로 관리하며 사용자 표시 문자열을 Java 코드에 하드코딩하지 않는다.
- 권한 요청 전 근거를 표시하고 거부, 다시 묻지 않음, 설정 변경 복귀 흐름을 모두 처리한다.
- 로그 태그와 로그 레벨을 일관되게 사용하고 릴리스 빌드에서 민감하거나 과도한 진단 로그를 제거한다.
- 라이브러리 버전은 Gradle에서 중앙 관리하고 검토되지 않은 동적 버전 표기를 사용하지 않는다.

### 13.3 테스트 규칙

- A*, 좌표 변환, 노드 스냅, 신뢰도 상태 전이는 JVM 단위 테스트로 검증한다.
- ARCore와 위치 공급자는 인터페이스로 감싸 fake 구현을 주입할 수 있게 한다.
- 주요 사용자 여정과 권한 거부 흐름은 계측/UI 테스트로 검증한다.
- 실제 기기 테스트는 최소 1대가 아니라 지원하려는 성능 등급별 대표 ARCore 기기군으로 수행한다.
- PR 병합 조건에 빌드, 단위 테스트, 정적 분석 통과를 포함한다.

## 14. 오류 및 예외 처리

| 상황 | 제품 동작 |
|---|---|
| 카메라 권한 거부 | AR을 비활성화하고 2D 지도 안내 및 권한 설정 방법 제공 |
| 위치 권한 거부 | 현재 위치 자동 탐색을 중단하고 출발 지점 수동 선택 제공 |
| Google Maps API 오류/할당량 초과 | 오류 원인과 재시도를 표시하고 가능한 경우 외부 Google Maps 앱으로 전환 |
| ARCore 미지원/업데이트 필요 | 지원 상태와 조치 방법을 표시하고 2D 모드 제공 |
| P0/P2 GPS·방향 정확도 저하 | AR 화살표를 숨기고 정확도 경고, 2D 지도, 센서 보정 및 출입구 수동 확인 제공 |
| 랜드마크 미인식 | 촬영 가이드, 다른 방향 스캔, 가까운 재측위 지점 안내 |
| 랜드마크 후보 충돌 | 위치를 확정하지 않고 추가 관측 요구 |
| ARCore 추적 손실 | AR 화살표 숨김, 천천히 주변을 비추도록 안내, 필요 시 재측위 |
| 지도/모델 버전 불일치 | 해당 데이터 활성화 금지, 이전 검증 버전 사용 또는 안내 제한 |
| 경로 없음 | AR 안내 중지, 원인과 대체 출입구/목적지 표시 |
| 네트워크 단절 | 캐시 데이터 사용, 없는 데이터는 다운로드 필요 상태 표시 |

- ARCore 추적 손실 횟수와 복구 시간

보존 기간과 수집 동의 정책은 배포 전 개인정보 검토를 거쳐 확정한다.

## 16. 테스트 및 검증 계획

### 16.1 데이터 검증

- 모든 목적지가 유효한 노드에 연결되어 있는지 검사한다.
- 양방향 간선 대칭성, 층 전환 연결, 금지 구역, 고립 노드를 자동 검사한다.
- 지도 축척과 실제 거리, 랜드마크 좌표와 기준 방향을 현장에서 검증한다.
- 모델 클래스 ID와 랜드마크 메타데이터 간 일치 여부를 빌드 또는 배포 전에 검사한다.

### 16.2 알고리즘 검증

- P0의 Places 결과와 지원 건물·출입구 데이터 매핑, Google 경로 요청/오류 처리와 응답의 공통 웨이포인트 변환을 테스트한다.
- P0/P2 공통으로 거리·방위 계산, 0°/360° 경계, 웨이포인트 전환, 방향 안정화, 위치 신뢰도와 도착 판정을 테스트한다.
- P2 자체 실외 경로 탐색의 연결 경로, 폐쇄 간선, 경로 없음, 위치 스냅, 이탈·재탐색을 테스트한다.
- 같은 층, 다층, 복수 출입구, 막힌 간선, 경로 없음 케이스를 테스트한다.
- 알려진 좌표 변환 입력에 대해 예상 AR Pose를 검증한다.
- 위치 노이즈, 잘못된 랜드마크 후보, VIO 드리프트를 재현해 상태 전이를 검증한다.

### 16.3 현장 검증

- P0 Google 보행 경로 및 P2 자체 경로와 실제 통행 가능 보행로·출입구의 일치 여부를 각각 확인한다.
- P0/P2는 주간/야간과 정지/보행 조건에서 GPS·방향 정확도, 웨이포인트 전환과 AR 화살표 반응을 반복 측정한다.
- 주간/야간, 밝음/어두움, 혼잡/비혼잡 조건에서 반복 측정한다.
- 서로 다른 카메라와 성능 등급의 ARCore 지원 단말에서 측정한다.
- 출입구부터 목적 강의실까지 end-to-end 테스트를 실시한다.
- 안전을 위해 계단, 유리문, 공사 구역에서 AR 표시가 실제 보행 판단을 방해하지 않는지 확인한다.

## 17. 단계별 출시 기준

### 17.1 P0 Google 경로 기반 실외 AR 내비게이션

- 파일럿 대상 건물의 공식명, 별칭, Google `placeId`, 대표 좌표, 출입구 및 도착 지점 데이터가 구축되어 있다.
- Google Places 기반 건물 검색, Routes API 보행 경로, 웨이포인트 진행, 카메라 AR 화살표와 건물 도착까지 핵심 여정이 연결된다.
- P0 및 P0/P1/P2로 표시된 요구사항 중 P0 범위의 수용 기준을 통과한다.
- 위치·카메라 권한 거부, GPS·방향 저정확도, Google API 오류·할당량 초과, 경로 이탈 및 네트워크 단절의 대체 흐름이 동작한다.
- 개인정보, 보행 안전, 접근성 점검을 완료한다.
- 3.2절의 P0 성공 지표를 파일럿 현장 테스트에서 충족한다.

### 17.2 P1 실내 강의실 안내

- P0 출시 기준을 계속 충족한다.
- 파일럿 건물의 승인된 평면도, 목적지, 그래프, 랜드마크 및 Vision Model 데이터가 10.5~10.6절의 품질 기준을 충족한다.
- 건물 출입구부터 실내 재측위, 층 전환, 목적 강의실 도착까지 핵심 여정이 연결된다.
- P1 및 복수 단계로 표시된 요구사항 중 P1 범위의 수용 기준을 통과한다.
- 치명적 경로 오류, 벽 통과, 잘못된 층 안내가 알려진 테스트 세트에서 발생하지 않는다.
- 카메라 권한 거부, ARCore 미지원, 추적 손실, 랜드마크 미인식의 대체 흐름이 동작한다.
- 3.2절의 P1 성공 지표를 파일럿 현장 테스트에서 충족한다.

### 17.3 P2 자체 경로 기반 실외 AR 내비게이션

- P0에서 검증한 건물·출입구 목적지 데이터를 자체 실외 안내에서도 동일하게 사용한다.
- P2 자체 실외 노드·간선 데이터와 경로 탐색 모델이 품질·무결성 기준을 충족한다.
- P0와 같은 GPS·방향·카메라 AR 파이프라인에 자체 경로의 웨이포인트가 연결된다.
- 자체 경로 탐색, 이탈·재탐색부터 카메라 방향 화살표, 저신뢰 처리와 건물 도착까지 핵심 여정이 연결된다.
- P2 및 복수 단계로 표시된 요구사항 중 P2 범위의 수용 기준을 통과한다.
- 위치·카메라 권한 거부, GPS 저정확도, 방향 센서 부정확 및 네트워크 단절의 대체 흐름이 동작한다.
- 경로 공급자를 P0 Google 또는 P2 자체 구현으로 교체해도 공통 AR 안내와 P1 실내 전환이 동일하게 동작한다.
- 3.2절의 P2 성공 지표를 파일럿 현장 테스트에서 충족한다.

| 잘못된 평면도 또는 그래프 | 통행 불가 경로 안내 | 자동 무결성 검사, 현장 승인, 운영 중 간선 비활성화 |
| 단말 성능 편차 | 낮은 FPS와 과열 | 추론 빈도·해상도 조절, 기기 등급 테스트, 제한 모드 |
| 화면 주시로 인한 보행 위험 | 안전 사고 | 진동·텍스트 보조, 경고 문구, 위험 구간에서 단순 안내 |

## 20. 미결정 사항

구현 착수 전에 다음 사항을 제품·개발·데이터 담당자가 확정해야 한다.

1. P0 파일럿 건물 목록, Google `placeId`와 P1 지원 층·강의실 목록
2. Routes API 응답에서 AR용 웨이포인트를 생성·병합하고 통과를 판정하는 기준
3. Google Maps Platform API 키 운영, 할당량, 비용 한도와 장애 대응 정책
4. P2 자체 실외 경로 탐색 모델의 알고리즘, 노드 간격, 비용 정책과 데이터 갱신 방식
5. Vision Model 형식, 입력 크기, 온디바이스 런타임 및 모델 배포 방식
6. 랜드마크별 실제 좌표와 기준 방향을 수집하는 도구 및 절차
7. 위치 확정, 경로 이탈, 도착 판정에 사용할 초기 임계값
8. 엘리베이터 대기 비용, 계단 선호도 및 접근성 경로 정책
9. 지도·모델 업데이트 서버 및 오프라인 캐시 보존 정책
10. 테스트 대상 기기와 최소 지원 Android API 수준
